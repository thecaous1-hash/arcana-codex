# 기능 설계 — 피드백 수집 & (반)자동 검토

배포 후 사용자에게 오류·개선사항을 받고, 그걸 Claude Code로 검토·수정하는 흐름.

---

## 1. 피드백 수집 메뉴 (앱 안)

- 앱에 **열고 닫는 피드백 버튼/패널** — 오류 신고·개선 제안 받기.
- 정적 사이트(GitHub Pages)라 앱 안에 DB를 못 두므로, 수집은 외부로 연결:
  - **옵션 A — GitHub Issues 링크:** 버튼 → 저장소 이슈 작성 페이지. 무료·간단, 단 작성자 GitHub 계정 필요.
  - **옵션 B — 구글 폼 등 외부 폼 링크:** 계정 없이 누구나 작성. 간단.
  - **옵션 C — 앱 내 댓글창 직접:** 매끄럽지만 글 저장에 별도 서버/DB 필요 → 정적 배포엔 부담(지금은 비권장).
- **권장:** 옵션 A 또는 B로 시작. (버튼 하나 = 링크 하나, 배포에 부담 없음)

## 2. Claude 검토·수정 시스템 — ⚠️ 현실과 이상 구분

### 이상(사용자가 원한 것)
> Claude가 주기적으로 스스로 점검 → 작은 건 허락 없이 웹에서 고치고 → 큰 건 사용자 호출해 검토.

### 현실 (중요 — 지금 되는 것/안 되는 것)
- ❌ **Claude는 스스로 주기적으로 돌지 않음.** 사용자가 말을 걸 때만 작동, 끝나면 멈춤. 백그라운드 자동 감시·자동 수정 기능 없음.
- ❌ **"허락 없이 자동으로 코드 수정·배포"는 불가능하며 안전하지도 않음.** (아무 감독 없이 자동 변경 = 사고 위험)
- ✅ **반자동은 가능:** 피드백을 한곳에 쌓아두고, 사용자가 원할 때 Claude Code가 몰아서 검토·수정.

### 현실적 워크플로우 (권장)
1. 피드백이 **GitHub Issues에 쌓임**(위 옵션 A).
2. 사용자가 원할 때(예: 주 1회) Claude Code에 요청:
   > "쌓인 피드백(이슈) 검토해줘. 간단히 고칠 수 있는 오류는 고치고, 큰 수정이 필요한 건 목록으로 정리해서 나한테 보고해줘. 고치기 전에 뭘 할지 먼저 알려줘."
3. Claude Code가 **작은 건 수정 제안 → 사용자 확인 → 반영**, **큰 건 보고만**.
4. 사용자가 커밋·푸시(또는 PR)로 반영.

### 진짜 자동화가 필요하면 (향후, 큰 작업)
- 사람 없이 정기 실행하려면 **GitHub Actions**(정기 스크립트) 같은 별도 인프라 필요.
- 자동 수정까지 가려면 "자동 테스트 → 통과 시에만 반영" 같은 안전장치가 전제. 복잡·위험 → **한참 뒤 별도 Phase.**

## 3. 단계

- **1단계(지금 가능):** 앱에 피드백 버튼(옵션 A/B) 추가.
- **2단계:** 이슈 검토를 "사용자 호출 시 Claude Code가 몰아서" 하는 루틴 정착.
- **3단계(향후):** GitHub Actions 등으로 정기 점검 자동화(안전장치 포함) — 큰 작업.

## 4. 주의

- 자동 수정은 **감독 없이는 하지 않는다**가 원칙. "작은 수정도 사용자 확인 후 반영"이 안전.
- 피드백 폼에 개인정보 수집 최소화(공개 앱).
